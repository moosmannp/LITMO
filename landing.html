What is MOMo?

Modular Ontology Modeling is a methodology for building ontologies out of reusable modules rather than as a single monolithic artifact. Its central commitment is that most of the work is conceptual — discussion, schema diagrams and documentation — and that the formal OWL file is only the final translation of decisions already made.

Modular, extensible, reusable — not a one-off

The problem is described deliberately loosely, often covering a set of related use cases and even future extensions currently out of scope, to keep the ontology suitable for adjacent purposes.

One key notion, one module

Key notions are derived from the use case, data sources and competency questions together. Each typically becomes a module, modeled in isolation while engineers watch cross-module compatibility.

Patterns as templates

Where a curated pattern library offers a close enough fit, the pattern serves as the template for the module. If none fits, the module is simply built from scratch.

Schema diagrams as prompts

The engineer sketches a tentative diagram from a naturally limited understanding and uses it to provoke domain experts into pointing out deficiencies. The draft need not be close to the final solution — its job is to get refined, modified or rejected outright.

Documentation is part of the ontology

A bare OWL file is hard to understand, and humans are who mostly deal with it. Each module's diagram is paired with its formal axioms and a natural-language reading of them.

Prefer scoped axioms over global ones

Rather than a global domain ∃R.⊤ ⊑ B, use a scoped ∃R.A ⊑ B. Scoped domain, range, functionality and cardinality axioms are easier to reuse and less likely to be wrong in a different context.

Provenance against feature creep

Tracing requirements from use cases → competency questions → key notions → modules keeps the scope honest and avoids premature generalization.

The ten MOMo steps

The methodology proceeds in ten steps, with responsibility shifting between the whole team and the ontology engineers. Green tags show where each step lives in this tool.

1
Describe use cases and gather possible data sources Panels 2–4
Responsible: entire team

The problem is described deliberately loosely — a paragraph can be enough, and it need not be crisp. It may cover several related use cases and future extensions. Alongside the problem, capture the existing data sources the ontology must represent or align against.

2
Gather competency questions Panel 5
Responsible: entire team

Competency questions are example queries of interest, in natural language, that the populated knowledge graph should answer. They refine the use case and sanity-check whether the data sources are adequate. Collecting them from potential future users works well; 10–12 sufficiently different questions are generally enough.

3
Identify key notions for the domain Panel 6
Responsible: entire team

The central step that sets up the modeling. Generalize the use case and competency questions into instance-free statements and note which noun terms recur. Human judgement is needed to surface implicit or "hidden" concepts — technically enslavement is a momentary event, but being enslaved is a state with temporal duration, and that state is likely the real key notion.

4
Identify existing ontology design patterns Panel 7
Responsible: ontology engineers

For each key notion, search a curated pattern library for a pattern close enough to serve as a template. A single notion may admit several reasonable choices — a Recipe could be a Document, a Plan or a Process — so consult the use case and competency questions to pick the best overall fit.

In this tool the library is the ODPA Patterns Repository: the model may only choose patterns that exist there, and the chosen pattern's actual classes and properties are handed to the generator as the module template.

5
Create schema diagrams for modules Panel 8
Responsible: entire team, led by ontology engineers

The intensive, synchronous heart of the process. Notions are modeled one at a time, starting with those that are central or clearly derivable from a pattern and deferring the controversial ones. Because diagrams are inherently ambiguous, engineers actively manage interpretation and ask experts concrete questions about intended meaning.

6
Set up documentation and determine axioms per module Panel 8
Responsible: ontology engineers & domain experts

Each module's schema diagram is paired with its formal OWL axioms plus a natural-language listing of them. Axioms here serve mainly to disambiguate meaning rather than to enable reasoning, so experts are asked pointed questions to pin them down.

7
Create the ontology-wide schema diagram Panel 8
Responsible: ontology engineers

Individual module diagrams are composed into a single combined diagram. The overriding priority is understandability — and the catch-all guideline is to break any other guideline if it makes the diagram clearer.

8
Add spanning axioms Partly in the tool
Responsible: ontology engineers

The whole ontology is examined for axioms spanning more than one module. These tend to be more complex, and are often easier for humans to write and read when expressed as rules. The tool writes class restrictions ("every A has some p to a B") during generation and offers them as a repair tool for class pairs the ontology connects only loosely.

9
Reflect on entity naming and all axioms Partly in the tool
Responsible: ontology engineers

Good, consistent names greatly aid reuse: singular and specific class names in CamelCase, lowercase verb-based property names with consistent inverses. It is fine to focus on structure during modeling and defer naming to here, since names are easy to change during documentation. The tool applies the project's naming conventions and checks the result with OOPS!.

10
Create the OWL file(s) Panel 8
Responsible: ontology engineers

The formal OWL file is produced last, reinforcing that most of the work is conceptual and the file is only the final translation. For maintainability it carries OPLa annotations identifying the modules and which pattern each was based on.

How the steps map onto the tool

The steps are consolidated into eight panels, so closely related steps share a workspace. Steps 8 and 9 are currently not covered by the tool.

PanelMOMo stepsWhat you do there
1 · Configure LLM—Choose a provider and model.
2 · Use Case & Data Sources1Describe the problem loosely; name data sources; upload files.
3 · Literature (optional)1Upload papers, existing ontologies and concept tables. Each paper is condensed into a paper card (concepts with definition, page and verified quote, relations, taxonomies, candidate questions); ontologies and tables are read directly. Everything is merged into a concept inventory with conflicts, candidate modules, and what existing ontologies already cover.
4 · Project Context1Confirm a drafted context document — purpose, scope, glossary, domain rules, data, reuse — answer targeted questions, and set conventions.
5 · Competency Questions2Draft and edit the questions the graph must answer.
6 · Key Notions & Modules3Define the few central concepts that each anchor a module; optionally ask for suggestions of missing ones.
7 · Patterns & Standards4Pick an ODPA design pattern per notion; select vocabularies to reuse.
8 · Model & Generate5, 6, 7, 10Generate and iterate on the modular ontology; inspect and export it.
⚠️ A note on the diagram steps. MOMo Steps 5 and 7 center on iterative, human-in-the-loop schema diagrams used as prompts to provoke domain experts. This tool renders a whole-ontology graph, which covers Step 7 reasonably well, but it does not replace Step 5's synchronous sketch–critique–refine sessions with domain experts. The tool supports that conversation; it does not substitute for it.
💡 Guidance, not gatekeeping. MOMo puts the OWL file last on purpose, and the tool shows you when conceptual steps are still missing — but it never blocks you. You can generate at any point and work backwards if that suits how your team works.
